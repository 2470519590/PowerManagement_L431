### 修正后的原因判断

根据“`0x8BBF5A` 对应板一直没有断电”的现场信息，之前把它判断为“恢复后该板没有上电”是不成立的，应予以撤销。

现有证据表明，问题发生在“只剩该板在线”切换到“另外三板恢复”的阶段：

- Session `06` 中，`0x8BBF5A` 连续发送 20 个 `0x121`，说明该板当时仍在运行，并且因为没有收到完整四板分配而持续重试。
- Session `07` 开始，该 token 不再出现；之后 Session `08~0B` 的另外三个 token 各自持续发送 20 个 `0x121`，但没有任何 `0x122/0x123`。
- L431 每约 `2.78 s` 发送一次新的 `0x120`，而装甲板侧枚举超时为 `4 s`。因此 L431 会在装甲板侧正常超时前反复清除 NodeID、重启枚举状态。
- 四块装甲板共用同一个 `0x121` 标准 ID。相同 ID 的不同数据不能依靠 CAN 仲裁区分，多个节点同时发送会产生数据位冲突，发送失败后进入重试。
- L431 的枚举收集逻辑在缺少节点时会持续接收重复 announce；重复 token 的候选项只有在“新候选项恰好是最后一项”时才删除。重复 announce 交错到达时，旧候选项会保留并占用 `collected_count`，最终可能触发 overflow/restart，进一步加剧重试。

因此当前最可能的根因是：四个节点同时使用固定 `0x121` 发送 UID，三板恢复后产生 announce 冲突和重复候选污染；L431 又以小于装甲板枚举超时的周期反复广播 `0x120`，使一直在线的 `0x8BBF5A` 节点被持续打断，最终表现为该节点从抓包中消失、系统无法收齐四个 UID。

这不是“L431 不能从三个节点恢复”的单一问题，而是“同 ID 多节点枚举协议 + L431 重试周期 + 重复候选处理”共同造成的恢复失败。

### 修复优先级

1. 先修 L431 收集表：以完整 UID 或 token 作为唯一候选，重复 announce 必须更新原候选，不能新建重复项；`collected_count` 只统计不同节点。
2. 把 L431 的下一轮 `0x120` 周期设为大于装甲板 `CAN_NODE_ENUM_TIMEOUT_MS`，或在一轮枚举未结束前禁止重新广播，避免持续打断装甲板。
3. 重新设计 `0x121` 多板响应时序。随机 hash 延迟不能保证无冲突；应采用 L431 分时授权、固定时隙加冲突重试，或使用能够参与仲裁的不同响应 ID。
4. 在修复前，不要用“恢复后三板能持续发送 `0x121`”判断系统接近成功；必须看到四个不同 token 的完整分片后再发送 `0x122`。

修复前判定：`[!]`。本次测试证明单节点和双节点恢复成功，但三节点恢复暴露了枚举协议在多节点重复 announce 和连续重启下的缺陷；`0x8BBF5A` 的供电不是首要嫌疑。该结论仅适用于修复前固件。
